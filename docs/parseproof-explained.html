ParseProof · how it works

ParseProof, explained simply

ParseProof pulls facts out of documents with AI, then proves every fact by pointing to the exact page and sentence it came from. This page walks through one document from start to finish and names every piece of technology on the way.

Python code (no AI) Extractor AI · gpt-4.1 Checker AI · gpt-4o A person

The big idea in one paragraph

Imagine a student doing a reading test on a 100-page book. The student must write each answer, the page number, and the exact sentence that proves it. A teacher then checks each answer by opening the book only on that page. If the page is wrong, the teacher uses the index at the back of the book to find the right page. A second teacher makes sure the first teacher's proof is real. Only the answers that fail get sent to the head teacher. In ParseProof, the student is one AI, the teacher is a different AI, the index and the proof-checking are plain Python, and the head teacher is your team.

Meet the cast

Checker AI

OpenAI gpt-4o. A different model on purpose. Looks at one page at a time and says right, wrong, or not here.

Python

Follow one field from start to finish

Say we upload a 100-page insurance policy and use the “Insurance policy” template, which asks for 14 fields. We will follow just one of them, total_premium. Every other field goes through the same steps at the same time.

Read the pages

Python

Like flipping through the book once and photocopying every page so you can search it later.

PyMuPDF opens the PDF and pulls out the text of each page, top to bottom and left to right, so columns stay together. If a page has no text (it is a scan or a photo), gpt-4.1-mini reads the picture and types out the words. That is called OCR.

Build the search index (the “RAG” part)

Python

Like writing the index at the back of the book before anyone asks a question.

For each page we make two things. An embedding: OpenAI turns the page into a list of 1,536 numbers that describe what it is about. Those go into FAISS. And a word count of every word on the page, which goes into BM25. The index is saved to disk, so it is built only once per document.

for page in pages:                          # all 100 pages, once
    meaning.append(embed(page))            # 1,536 numbers per page  -> FAISS
    words.append(count_words(page))        # word counts per page    -> BM25
save_to_disk()

The extractor checks its own work

Pythongpt-4.1, only if needed

Before handing in the test, the student checks each copied sentence is really in the book. If one isn't, they open that page again and copy it properly.

Python looks for every quote in the document's text. If a quote can't be found anywhere, only that field goes back to gpt-4.1, once, with the page's real text and a picture of the page. The new answer is kept only if its quote is on the page. Most runs skip this step because every quote is found. See Why the same bill can pass once and fail the next time.

Find the proof on the page

Python

The teacher opens to page 7 and checks the copied sentence is really there.

rapidfuzz does a forgiving Ctrl+F. It gives a score from 0 to 100 for how well the quote matches the page. 85 or more counts as found. It is forgiving because PDFs often have odd spacing or line breaks.

if fuzzy_match(quote, page_text[7]) >= 85:
    go_to("verify", pages=[7])      # found it: check only page 7
else:
    go_to("search")                 # wrong page or made-up quote

Search, only if needed

Python

The page number was wrong, so the teacher uses the index at the back of the book.

Hybrid search (FAISS + BM25, merged, then reranked) picks the 3 pages most likely to hold the answer. The section How the search works below explains it step by step. Most fields skip this step because the quote was found in step 4.

Check the value

gpt-4o

A second teacher, who did not write the answer, checks it against the page.

The checker gets only page 7 (its text and a picture of it), the field description, and the claimed value. It must answer one of three things and copy the sentence that proves it.

{ "verdict": "correct",            # or "incorrect" or "not_found"
  "correct_value": "$12,400.00",
  "proof": "Total annual premium payable: $12,400.00" }

Check the checker

Python

Even teachers make mistakes, so we check their proof too.

rapidfuzz checks the checker's proof is really on the page. Then Python checks the value is inside the proof, with every digit matching exactly. If the proof is fake, the field goes to a person. If the checker said “incorrect” or “not found”, we search other pages once and check again.

One last rule: if the checker's “correct value” has exactly the same words as the extracted value, just with a repeat removed or in a different order, it isn't a real mistake. That counts as verified.

Maths and rule checks

Python

Does the answer add up?

Templates can have sum rules like premium + taxes_and_fees = total_cost or paid + reserves = incurred. Python also checks required fields are filled, numbers are numbers, and dates are dates.

A person reviews the flagged fields

Person

The head teacher looks only at the answers marked red.

Each field ends as Verified, Mismatch or Needs review. The review screen highlights the proof on the PDF. The reviewer clicks “Use verified value”, “Keep extracted” or edits the value, then approves and exports JSON or CSV.

It does not extract twice and compare

Not this

Extract with AI. Extract again with RAG. Compare the two lists.

This

Extract once with AI. RAG only finds where to look. A second AI checks the answer on that one page, and Python checks the proof is real.

Why? Checking 1 page is much cheaper and faster than re-reading 100, and every answer comes with proof you can see, not just a second guess.

How the search works

This is the “RAG” part (Retrieval-Augmented Generation: find the right text first, then give it to the AI). The search for "total premium" narrows down in rounds, from cheap and rough to slow and careful.

100pages

FAISS (meaning). Turn the question into 1,536 numbers and compare them with every page's numbers. Pages about the same idea score high, even with different words, like “amount payable for coverage”. This is just maths, so it takes a few milliseconds.

100pages

BM25 (words). Score every page by how often it uses the words “total” and “premium”, with rare words counting more. This catches exact things that meaning search misses, like a policy number POL-88213.

10pages

Merge (RRF). Combine the two top-10 lists into one. A page that ranks well on both lists rises to the top.

3pages

Rerank (cross-encoder). A small AI model that runs on our own computer, not OpenAI, reads the question and each of the 10 pages side by side and scores how well they match. The best 3 go to the checker.

The merge step, with real numbers

RRF stands for Reciprocal Rank Fusion. Each list gives a page 1 ÷ (60 + its rank) points, and we add them up. The 60 stops one list from shouting over the other.

PageRank in FAISSRank in BM25ScoreResult

Why not just use the reranker on all 100 pages? It is the most accurate, but also the slowest. FAISS and BM25 are fast and rough, so they choose 10 pages for the reranker to read carefully.

Why the same bill can pass once and fail the next time

Sooner or later your team will run the same document twice and get two different results. Here is a real case from a phone and wifi bill, the three reasons it happens, and the three safety nets ParseProof now uses. (The name and address below are made up. The layout is the real one.)

What happened

Run A · Mismatch

The extractor wrote the billing address as

Customer Name Tamil Nadu, 600001

The two street lines are missing.

Run B · Verified

The extractor wrote

Customer Name 12/3, Green Park Colony, Lake Street, Northfield, Temple Road, Townpur, Tamil Nadu, 600001

In Run A the checker did its job. It opened page 3, found the full address, and flagged the difference. So the mismatch was real: the extractor had misread the page. The question is why the same model read the same page differently.

Reason 1: AI writes its answer one small piece at a time

An AI model doesn't look an answer up like a database. It writes the answer one small piece at a time. Each piece is called a token and is about three quarters of a word. Before every piece, the model works out a list of possible next pieces, each with a chance. For this address it might look like this:

Billing address: Customer Name ▍

12/352%
Tamil47%
other1%

The numbers above are made up to show the idea. We can't see the real ones.

Temperature is a setting for how adventurous the model is. At a high temperature it sometimes picks a less likely piece, which is useful for writing poems. ParseProof always uses temperature 0, which means “always take the most likely piece”.

Reason 2: “always the most likely” isn't perfectly steady

When two choices are almost tied, like 52% and 47% above, tiny rounding differences can swap which one comes first. OpenAI's servers work on many people's requests together, and the exact arithmetic changes very slightly depending on what else is in the batch. Nobody outside OpenAI can control that. Once one piece flips, everything after it follows a different path. If the model writes “Tamil” right after the name, it carries on with “Nadu, 600001” and never goes back for the street.

Like two runners who finish 1 millisecond apart. Time them with two slightly different stopwatches and the winner can change.

Reason 3: this page is a close call

Near-ties happen when a page is confusing, and this one is. The address sits beside a second column with a barcode, the bill number and “Place of Supply”. Besides what you see, a PDF stores its words as hidden text with positions, called the text layer. Read that text layer in order and three lines from the right-hand column land in the middle of the address.

The extractor looks at both the picture of the page and its text layer. Most of the time it follows the address down correctly. Now and then it jumps from the name to “Tamil Nadu, 600001” and drops the lines in between. That is Run A.

The three safety nets

A clearer instruction

Prompt for gpt-4.1

Writing “show every step” at the top of a maths test.

The prompt is the written instructions sent with every request. We added one rule: “Values like addresses span several lines. Include every line of the block, in order. Never skip a line in the middle of a block.” Clear rules make near-ties rarer, but they can't remove them completely.

A self-check before the checker

Pythongpt-4.1

The student checks every copied sentence against the book before handing in the test.

In Run A the extractor's quote was “Billing Address Customer Name Tamil Nadu, 600001”. That sentence isn't anywhere in the document, so it was a clue the answer was wrong. Now Python spots that clue straight away. It uses rapidfuzz, a forgiving Ctrl+F that scores how closely two pieces of text match, from 0 to 100. Below 85 means not found.

for field in answers:
    if not found_in_document(field.quote):         # rapidfuzz score below 85
        needs_reread.append(field)

if needs_reread:                                # most runs: empty, no extra cost
    new = ask_gpt41(page_text, page_picture,       # the page's real text + a photo of it
                    "your quote isn't on the page, read it again")
    if found_in_document(new.quote):             # trust it only if the proof is real
        use(new)

This is called grounding: an answer must be tied to its source. On the Run A page, the re-read came back with the full address. The field's notes say when a re-read happened, so nothing is hidden. It costs one extra AI call, and only when a quote is missing.

A same-words rule after the checker

Python

If two students write the same address but one writes the city twice, nobody marks it wrong.

This bill prints “Townpur, Tamil Nadu, 600001” twice. Once the extractor copied every line, the checker started calling the copy without the repeat “the correct value”, which turned a harmless difference into a mismatch. Now Python compares the two values word by word:

  • A regular expression (a search pattern for text) splits each value into words made of letters, digits and slashes, and ignores commas and capitals.
  • The words go into a set, a list where repeats collapse and order doesn't matter.
  • If both sets are exactly the same, and there are at least 4 words, it is the same value, so it counts as Verified. This applies only to text fields. Numbers and dates still have to match exactly.

Can we make the AI 100% repeatable?

No. No setting does that, for any AI model today. That is exactly why ParseProof has a second AI as checker, and Python checks that both AIs' proof is really on the page. With the safety nets, a mismatch is now much more likely to be a real problem in the document, like the wrong GSTIN, than a slip by the extractor.

Questions your team might ask

Why not ask the same AI to check itself?

A model tends to repeat its own mistakes. A different model, looking only at the page, catches more of them.

Why do we need Python checks if we have two AIs?

AIs can invent text. Python cannot. If either AI claims a sentence is on the page and Python can't find it, we don't trust the answer.

Does the search send all 100 pages to OpenAI every time?

No. All 100 pages are turned into numbers once, at upload. Each search sends only the short question to OpenAI. The comparing, merging and reranking all run on our computer.

Why did the same document fail once and pass the next time?

AI writes its answer one piece at a time, and on a confusing page two choices can be almost tied. Tiny differences on OpenAI's servers can tip it either way. The full story is above. The self-check now fixes most of these slips before you see them.

What does a person still have to do?

Only look at fields marked Mismatch or Needs review, choose the right value, and approve the run.
