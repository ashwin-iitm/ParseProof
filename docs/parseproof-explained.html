ParseProof · how it works

How ParseProof reads a document and proves every answer

We follow one made-up insurance policy from the moment you upload it to the moment you export the data. Every box on this page is a real step in the code, and the colour tells you who does it.

Python code (no AI) Extractor AI · gpt-4.1 Checker AI · gpt-4o You

The two questions everyone asks first

Does Python read the PDF and send its text to the AI? No. The PDF file itself goes to the AI.

For a PDF, ParseProof sends the actual file to gpt-4.1. OpenAI reads its text and looks at a picture of every page, so tables, stamps and scans work. Python also reads the pages, but only to build a search index and to check quotes later. Python's text is not what the extractor reads.

Excel, Word and CSV files are different. The AI can't take those files directly, so Python turns them into text first and sends that text.

If Python finds the exact quote on the page, does the checker AI still run? Yes. The checker AI always runs.

Python answers “is this sentence really on page 2?” It can't answer “is this the right value for this field?” A sentence can be real and still be the wrong answer, for example the flood deductible instead of the policy deductible. So every field gets one gpt-4o check. The only time no checker AI runs is when no page can be found at all.

Step by step, with the policy

You upload the file

Python

Handing the policy to the office.

The server saves policy.pdf, counts its 60 pages, and refuses it early if it is password-protected. You pick the Insurance policy template and click Extract and verify.

Python reads every page and builds the index

Pythongpt-4.1-mini, page 58 only

Photocopying every page and writing the index at the back of the book, before anyone asks a question.

  • PyMuPDF takes the text of each page, top to bottom and left to right.
  • Page 58 is a scan with no text, so gpt-4.1-mini reads its picture and types out the words. This is OCR. Only pages with almost no text get OCR.
  • Each page becomes 1,536 numbers that describe its meaning (an embedding, made by OpenAI's text-embedding-3-small). These go into FAISS.
  • Each page's words are counted for BM25.
  • The index is saved to disk under the file's fingerprint, so the next run of the same file skips all of this.

This index is for the checker. The extractor never reads it.

The extractor AI reads the PDF and answers in JSON

gpt-4.1

The student answers every question and, for each one, writes the page number and copies the sentence that proves it.

ParseProof sends the PDF file with the list of 14 fields and their descriptions. A strict JSON schema forces the answer into the same shape every time, and temperature 0 keeps it as repeatable as possible.

The extractor fell for the trap: it took the flood deductible from page 41. It also found no broker. The pages 41–60 call runs at the same time and returns its own answers; for each field Python keeps the most confident non-empty one.

Python fixes page numbers and runs the self-check

Pythongpt-4.1, only if needed

Before handing in the test, the student checks every copied sentence is really in the book.

  • Page numbers: AI page numbers can drift by one or two. Python searches for each quote with rapidfuzz (a forgiving Ctrl+F that scores 0–100; 85 or more counts as found). If “Policy No. NSI-CGL-2026-004512” is really on page 2, the page becomes 2, whatever the AI said.
  • Self-check: if a quote can't be found anywhere in the document, that field goes back to gpt-4.1 once, with the page's real text and a picture of it. The new answer is kept only if its quote is on the page. In our policy every quote is found, so this step costs nothing.

One QC agent per field checks the answer

Pythongpt-4o

A second teacher, who did not write the answers, opens the book on the page the student named and checks each answer there.

All 14 fields are checked at the same time, up to 8 AI calls at once. Each field goes through the same four steps. The next section shows them as a diagram, with what happens to the deductible.

Rule checks

Python

Does the answer add up?

Python checks that required fields are filled, that numbers are numbers and dates are dates, and the template's sum rule: premium + taxes_and_fees = total_cost. Here ₹4,20,000 + ₹75,600 = ₹4,95,600, so it passes.

Inside one QC agent

The policy number: the simple path

  • Locate (Python): “Policy No. NSI-CGL-2026-004512” is on page 2, score 100. Go to verify with page 2.
  • Verify (gpt-4o): reads page 2 only and answers “correct”, with its own proof quote.
  • Check the checker (Python): its proof is on page 2. Decide: Verified.

One AI call. This is what happens to most fields.

The deductible: why the checker AI must run even when the quote is found

  1. Locate (Python): “Flood deductible: ₹2,50,000 per occurrence” is on page 41, exactly. Python is satisfied that the sentence is real.
  2. Verify (gpt-4o), first try: it reads page 41 and sees a flood add-on, not the policy's deductible. Verdict: “not found on these pages”.
  3. Search once more (Python): the index is asked for “deductible, deductible or self-insured retention amount, ₹2,50,000” and returns pages 2, 7 and 18. The next section shows how.
  4. Verify (gpt-4o), second try: it reads pages 41, 2, 7 and 18 together and answers “incorrect, the deductible is ₹50,000”, with the proof “Deductible: ₹50,000 each claim” on page 2.
  5. Check the checker (Python): the proof is on page 2, and the digits 50000 are in it. Decide: Mismatch. The review screen shows ₹2,50,000 crossed out and ₹50,000 suggested, with page 2 highlighted.

So: Python finding the quote is necessary, not enough

Python proves a sentence exists. Only an AI can tell whether that sentence answers the field. Without the checker, the flood deductible would have gone into your spreadsheet as the policy deductible, with a perfect quote next to it. That is why every field gets a gpt-4o check, and why Python then checks gpt-4o's proof in turn.

The broker: a field that isn't there

  • Locate (Python): nothing was extracted, so there's no quote to look for. Go straight to search.
  • Search: the best 3 pages for “broker name, insurance broker, agent or producer”.
  • Verify (gpt-4o): “not found”. Broker is not a required field, so Decide gives Verified, with the note “Confirmed absent on the pages checked”. If it were required, it would be Needs review.

How the search finds the right page

This is the “RAG” part (Retrieval-Augmented Generation: find the right text first, then give only that to the AI). It only runs when the checker needs other pages. For the deductible, the search question is the field name, its description and the extracted value: deductible · Deductible or self-insured retention amount · ₹2,50,000.

60pages

FAISS: search by meaning. The question is turned into 1,536 numbers, the same way every page was. FAISS compares them with all 60 pages and lists the 10 closest in meaning. It finds pages about deductibles even if they use other words, like “self-insured retention”.

60pages

BM25: search by words. At the same time, every page gets a score for how often it uses the question's words. Rare words count more than common ones, and long pages don't win just by being long. It catches exact things meaning search can miss, like “₹2,50,000”. Top 10 again.

≤10pages

RRF: merge the two lists. Each list gives a page 1 ÷ (60 + its rank) points, and the points are added. A page that is high on both lists rises to the top.

3pages

Cross-encoder: read carefully. A small AI model running on your own computer (not OpenAI) reads the question and each of those pages side by side and scores how well they match. The best 3 new pages go to the checker.

Scores are made up to show the idea. Page 41 was already checked, so the 3 new pages are 2, 7 and 18, and the checker reads them together with 41. Long pages are read in windows of 1,500 characters (overlapping by 300), and a page's score is its best window.

Why not only FAISS and BM25?

They are fast but rough. Each makes its fingerprint of the question and the page separately, so neither ever reads them together.

Why not only the cross-encoder?

It is the most accurate but the slowest. Reading 10 pages is quick; reading all 60 for every search would not be. So FAISS and BM25 pick 10, and the cross-encoder picks 3.

Why answers can differ between two runs

An AI writes its answer one small piece at a time and picks the most likely next piece. When two choices are almost tied, tiny differences on OpenAI's servers can tip it either way, even at temperature 0. That's why ParseProof never trusts one AI alone: the self-check, the second AI and Python's proof checks are there to catch a slip before it reaches your spreadsheet.
